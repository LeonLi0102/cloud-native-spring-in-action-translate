云原生应用是高度分布式的系统，它们运行在云中，对变化的适应能力很强。系统由多个服务组成，这些服务通过网络进行通信，并部署在动态环境中，其中所有内容都在不断变化。

在深入研究 Spring、Docker 和 Kubernetes 之前，最基本的是首先定义什么是云原生。像我们领域中的其他流行语（如敏捷、DevOps 或 微服务）一样，云原生有时会被误解，并且可能会引起混淆，因为它对不同的人意味着不同的事情。

在本章中，我将为您提供本书其余部分所需的概念。首先，我将定义云原生并说明一个应用成为云原生应用所需的条件。我将解释云原生应用程序的属性，考查云计算模型的特性，并讨论您应该何时以及为什么要迁移到云。我还将介绍一些云原生拓扑和体系结构的基本概念。图 1.1 显示了我将在本章中介绍的所有不同元素的概述，以定义和限定云原生系统。在本章的最后，您将开始使用 Spring 构建云原生应用程序并使用 Kubernetes 部署它们的旅程。

1.8 总结

  • 云是一种 IT 基础设施，以商品的形式提供计算、存储和网络资源。用户只为实际使用的资源付费。
  • 云原生应用程序是专为云端运行的应用而设计的高度分布式系统。
  • 云服务商以不同的抽象级别提供服务：基础设施即服务（IaaS）、容器即服务（CaaS）、平台即服务（PaaS）、功能即服务（FaaS）或软件即服务（SaaS）。
  • 云原生应用程序具有水平可扩展性、松散耦合性和高度内聚性，具有故障恢复能力、可管理性和可观察性。
  • 云原生开发由自动化、持续交付和 DevOps 支持。云原生是一种文化，支持不同角色之间的协作，以共同交付业务价值。
  • 现代企业采用云原生技术开发快速交付的软件，可根据需求动态缩放，且始终可用，在优化成本的同时具有故障恢复能力。
  • 容器可以用作计算单元来设计云原生系统。它们比虚拟机更轻量，并提供可移植性、不变性和灵活性。如：Docker。
  • 专用平台提供管理容器的服务，而无需直接处理底层。它们提供容器编排、集群管理、网络服务和调度。如：Kubernetes。
  • 无服务器模式是一种云服务商管理服务器和后端函数的模式，而开发人员只需关注业务逻辑。后端函数在每次使用时计费，以实现成本优化。如：Google Functions。
  • 微服务架构可以用于开发云原生应用程序，但并不是必须的。云原生与微服务不完全相同。
  • 要设计云原生应用程序，您可以使用 基于服务 的架构，其要素是：服务和交互。服务可以进一步分为：应用程序服务（无状态）和数据服务（有状态）。

第 4 章 配置管理外部化

本章内容：

在上一章中，您构建了一个用于管理图书目录的 RESTful 应用程序。作为实现的一部分，您定义了一些数据来配置应用程序的某些方面（在文件中）。例如，Tomcat 线程池或连接超时时间。下一步可能是将应用程序部署到不同的环境：首先是测试环境，然后是预发环境，最后是生产。如果您需要每个环境的都有不同的 Tomcat 配置，如何做到这一点呢？

传统的应用程序通常打包为一个应用包，包括源代码和一系列配置文件。包含不同环境的配置数据，并在运行时标记。这意味着您需要更新特定环境的配置数据时，都必须构建一个新的应用程序包。这一过程的一个改进是为每个环境创建不同的构建，但这意味着您无法保证在预发环境中运行的内容，在生产环境中也会以同样的方式运行，因为它们是不同的打包制品。

配置（Configuration）定义为在部署之间可能发生更改的一切（根据 十五要素 方法论），如凭据、资源处理程序和支持服务的 URL。根据部署位置的不同，同一应用程序将有不同的需求，并且很可能需要不同的配置。云原生应用程序的一个关键特性是，应用程序制品将在整个环境中保持不变。无论将其部署到哪个环境，都不会更改应用程序制品。

您部署的每个版本都是构建和配置的组合。可以使用相同的构建部署到具有不同配置数据的不同环境，如图 4.1 所示。

图 4.1 您部署的每个版本都是构建和配置的组合，每个环境都不同。

可能需要跨部署进行更改的任何内容，都应该是可配置的。例如您可能希望更改凭据以访问支持服务、功能标志和数据库资源或外部 API 的 URL，所有这些都取决于您正在部署应用程序的环境。云原生应用程序支持配置外部化，因此您可以替换它，而无需重新生成代码。关于凭据，它甚至更重要，关键是不要将它们与应用程序代码一起存储。无数的数据泄露，都因为向公开的存储库提交了凭据信息。确保您不会是他们中的一员。

5.3 使用 Spring 和 Testcontainers 测试数据持久化

在前面的章节中，我们通过针对容器中的 PostgreSQL 数据库进行开发，为应用程序添加了数据持久化功能，这与生产环境中使用的技术相同。这是迈向 15 要素方法论推荐的环境一致性的重要一步。保持所有环境尽可能相似可以提高项目的质量。

数据源是环境差异的主要原因之一。在本地开发时使用内存数据库（如 H2 或 HSQL）是常见做法，但这会影响应用程序的可预测性和健壮性。即使所有关系型数据库都使用 SQL 语言，Spring Data JDBC 提供通用抽象，但每个供应商都有自己的方言和独特功能，因此在生产环境中使用与开发和测试相同的数据库至关重要。

Docker 使在本地使用实际数据库设置和开发应用程序变得更容易，正如您在 PostgreSQL 中体验的那样。类似地，Testcontainers（一个用于测试的 Java 库）使在集成测试中使用后端服务作为容器变得简单。

本节将展示如何使用 @DataJdbcTest 注解为数据持久化层编写切片测试，以及如何使用 @SpringBootTest 注解在集成测试中包含数据库。在两种情况下，都将依赖 Testcontainers 针对实际的 PostgreSQL 数据库运行自动化测试。

5.3.1 为 PostgreSQL 配置 Testcontainers

Testcontainers（https://testcontainers.org）是一个用于测试的 Java 库。它支持 JUnit，提供轻量级、一次性的容器，如数据库、消息代理和 Web 服务器。它非常适合实现与生产中使用的实际后端服务的集成测试。结果是更可靠和稳定的测试，从而带来更高质量的应用程序并有利于持续交付实践。

您可以使用 Testcontainers 配置轻量级 PostgreSQL 容器，并在涉及数据持久化层的自动化测试中使用它。

首先，需要在 Catalog Service 项目的 build.gradle 文件中添加 Testcontainers PostgreSQL 模块的依赖。添加新依赖后记得刷新或重新导入 Gradle 依赖。

代码清单 5.16 在 Catalog Service 中添加 Testcontainers 依赖

ext {
    ...
    set('testcontainersVersion', "1.17.3")
}

dependencies {
    ...
    testImplementation 'org.testcontainers:postgresql'
}

dependencyManagement {
    imports {
        ...
        mavenBom "org.testcontainers:testcontainers-bom:${testcontainersVersion}"

}

运行测试时，我们希望应用程序使用 Testcontainers 提供的 PostgreSQL 实例，而不是之前通过 spring.datasource.url 属性配置的实例。我们可以在 src/test/resources 下创建的新 application-integration.yml 文件中覆盖该值。启用 integration 配置文件时，此文件中定义的任何属性将优先于主配置文件中的属性。

在 src/test/resources 中创建新的 application-integration.yml 文件，并添加以下配置。

  datasource:

5.3.2 使用 @DataJdbcTest 和 Testcontainers 测试数据持久化

Spring Boot 提供了一些测试切片，可以只加载应用程序的特定部分。@DataJdbcTest 注解会自动配置内存数据库、实体和仓库的扫描，以及 JDBC 相关的组件。默认情况下，它使用嵌入式数据库，但我们可以覆盖它以使用 Testcontainers。

创建一个新的 DataPersistenceTests 类，并添加以下代码：

代码清单 5.18 使用 @DataJdbcTest 和 Testcontainers 测试数据持久化

package com.polarbookshop.catalogservice.data;

import com.polarbookshop.catalogservice.domain.Book;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.data.jdbc.DataJdbcTest;
import org.springframework.test.context.ActiveProfiles;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import static org.assertj.core.api.Assertions.assertThat;

@DataJdbcTest
@Testcontainers
@ActiveProfiles("integration")
class DataPersistenceTests {

    @Container
    static PostgreSQLContainer<?> postgresql = new PostgreSQLContainer<>("postgres:14.4");

    @Autowired
    private BookRepository bookRepository;

    @Test
    void shouldCreateAndRetrieveBook() {
        var book = Book.of("1234567891", "Northern Lights", "Lyra Silverstar", 9.90);
        var savedBook = bookRepository.save(book);

        var retrievedBook = bookRepository.findByIsbn(savedBook.isbn());
        assertThat(retrievedBook).isPresent();
        assertThat(retrievedBook.get().title()).isEqualTo("Northern Lights");
    }
}

5.3.3 使用 @SpringBootTest 和 Testcontainers 进行集成测试

@SpringBootTest 注解加载完整的应用程序上下文，更适合测试应用程序的各个层如何协同工作。我们可以结合使用 @SpringBootTest 和 Testcontainers 来针对实际的 PostgreSQL 数据库运行集成测试。

代码清单 5.19 使用 @SpringBootTest 和 Testcontainers 进行集成测试

package com.polarbookshop.catalogservice;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.context.ActiveProfiles;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
@Testcontainers
@ActiveProfiles("integration")
class CatalogServiceApplicationTests {

    @Container
    static PostgreSQLContainer<?> postgresql = new PostgreSQLContainer<>("postgres:14.4");

    @Autowired
    private BookRepository bookRepository;

    @Test
    void contextLoads() {
        assertThat(bookRepository).isNotNull();
    }
}

5.4 使用 Flyway 管理生产环境中的数据库

记录任何数据库更改是很好的做法，就像您通过版本控制管理应用程序源代码一样。您需要一种确定性和自动化的方式来推断数据库的状态、是否已应用特定更改、如何从头重新创建数据库以及如何以可控、可重复和可靠的方式迁移它。持续交付方法鼓励尽可能自动化，包括数据库管理。

在 Java 生态系统中，最常用的跟踪、版本控制和部署数据库更改的两个工具是 Flyway（https://flywaydb.org）和 Liquibase（https://liquibase.org）。它们都与 Spring Boot 完全集成。本节将展示如何使用 Flyway。

5.4.1 理解 Flyway：数据库的版本控制

Flyway 是一个为数据库提供版本控制的工具。它为数据库状态的版本提供单一真相来源，并增量跟踪任何更改。它自动化更改，让您可以重现或回滚数据库的状态。Flyway 高度可靠，在集群环境中安全使用，并支持多种关系型数据库，包括 Amazon RDS、Azure Database 和 Google Cloud SQL 等云数据库。

注意：本节将介绍 Flyway 提供的一些功能，但建议您查阅官方文档以发现此工具提供的所有强大功能（https://flywaydb.org）。

Flyway 的核心是管理数据库更改。任何数据库更改都称为迁移，迁移可以是版本化的或可重复的。版本化迁移由唯一版本号标识，按顺序恰好应用一次。对于每个常规版本化迁移，您还可以提供可选的撤消迁移以恢复其效果（以防出现问题）。它们可用于创建、更改或删除关系对象（如模式、表、列和序列）或更正数据。另一方面，可重复迁移在其校验和更改时每次都会应用。它们可用于创建或更新视图、存储过程和包。

两种类型的迁移都可以在标准 SQL 脚本（适用于 DDL 更改）或 Java 类（适用于 DML 更改，如数据迁移）中定义。Flyway 通过在首次运行时自动在数据库中创建的 flyway_schema_history 表来跟踪哪些迁移已应用。您可以将迁移想象为 Git 仓库中的提交，模式历史表包含随时间应用的所有提交列表（图 5.6）。

图 5.6 Flyway 迁移表示数据库更改，可以想象为 Git 仓库中的提交。

注意：使用 Flyway 的前提是您要管理的数据库和具有正确访问权限的用户都存在。一旦有了数据库和用户，Flyway 就可以为您管理数据库更改。您不应该使用 Flyway 来管理用户。

7.3 服务发现和负载均衡

在微服务架构中，服务需要能够找到彼此。Kubernetes 提供了内置的服务发现和负载均衡机制。

7.3.1 理解服务发现和负载均衡

服务发现 — 允许服务找到其他服务的网络位置。在 Kubernetes 中，Pod 是短暂的，可以随时创建和销毁。服务发现允许服务通过稳定的服务名称访问其他 Pod，而不需要知道具体的 IP 地址。

负载均衡 — 将网络流量分发到多个 Pod，以确保高可用性和可扩展性。Kubernetes Service 自动在后端 Pod 之间进行负载均衡。

7.3.2 客户端服务发现和负载均衡

客户端服务发现意味着客户端负责查询服务注册表并选择可用的后端实例。在 Kubernetes 中，这可以通过环境变量或 DNS 实现。

7.3.3 服务端服务发现和负载均衡

服务端服务发现意味着客户端向负载均衡器发送请求，负载均衡器查询服务注册表并将请求转发到可用的后端实例。Kubernetes Service 就是这种模式的实现。

7.3.4 使用 Kubernetes Service 暴露 Spring Boot 应用程序

Service 是 Kubernetes 中用于暴露应用程序的对象。它为一组 Pod 提供稳定的网络端点。

Service 类型：

  • ClusterIP — 仅在集群内部可访问（默认）
  • NodePort — 在每个节点上暴露端口，可从外部访问
  • LoadBalancer — 使用云提供商的负载均衡器暴露服务

Service YAML 示例：

apiVersion: v1
kind: Service
metadata:
  name: catalog-service
spec:
  type: LoadBalancer
  selector:
    app: catalog-service
  ports:
  - port: 9001
    targetPort: 9001

$ kubectl apply -f catalog-service-service.yaml

$ kubectl get services

8.1 使用 Reactor 和 Spring 的异步非阻塞架构

响应式宣言（www.reactivemanifesto.org）将响应式系统描述为响应式的、有韧性的、弹性的和消息驱动的。其构建松散耦合、可扩展、有韧性和经济高效的应用程序的使命与我们对云原生的定义完全兼容。

8.1.1 从每请求一线程到事件循环

在非响应式应用程序中，每个请求分配一个线程。在返回响应之前，线程不会用于其他任何事情。这就是每请求一线程模型。当请求处理涉及 I/O 等密集操作时，线程将阻塞，直到这些操作完成。

响应式应用程序在设计上更具可扩展性和效率。在响应式应用程序中处理请求不涉及专门分配给定线程——请求基于事件异步完成。这种称为事件循环的范式不会对应用程序的可扩展性设置硬性约束。

8.1.2 Project Reactor：使用 Mono 和 Flux 的响应式流

响应式 Spring 基于 Project Reactor，一个用于在 JVM 上构建异步、非阻塞应用程序的框架。Reactor 是 Reactive Streams 规范的实现。

Reactor 中的两个核心类型：

  • Mono — 表示 0 或 1 个元素的异步序列
  • Flux — 表示 0 到 N 个元素的异步序列

8.1.3 Spring 响应式栈

Spring 框架提供了全面的响应式支持：

  • Spring WebFlux — 响应式 Web 框架，替代 Spring MVC
  • Spring Data R2DBC — 响应式数据库访问
  • Spring Security Reactive — 响应式安全

9.2 使用 Circuit Breaker 和 Resilience4j 实现容错

在分布式系统中，服务之间的调用可能会失败。为了防止级联故障，我们需要实现容错模式。

9.2.1 理解断路器模式

断路器模式类似于电路断路器：当失败率超过阈值时，断路器打开，阻止进一步调用，从而保护下游服务和系统资源。

断路器有三种状态：

  • 关闭（Closed） — 正常状态，请求正常通过
  • 打开（Open） — 故障状态，所有请求立即失败
  • 半开（Half-Open） — 恢复状态，允许部分请求通过以测试服务是否恢复

9.2.2 配置断路器

spring:
  cloud:
    gateway:
      routes:
        - id: catalog-route
          uri: http://localhost:9001
          predicates:
            - Path=/books/**
          filters:
            - name: CircuitBreaker
              args:
                name: catalogService
                fallbackUri: forward:/fallback/catalog

配置 Resilience4j 断路器：

resilience4j:
  circuitbreaker:
    instances:
      catalogService:
        slidingWindowSize: 10
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
        permittedNumberOfCallsInHalfOpenState: 3

10.1 事件驱动架构

事件是一个发生的事情。它是系统中发生的相关内容，如状态变化，可能有多种事件来源。当事件发生时，相关方可以收到通知。事件通知通常通过消息完成，消息是事件的数据表示。

在事件驱动架构中，我们识别事件生产者和事件消费者。生产者是检测事件并发送通知的组件。消费者是当特定事件发生时被通知的组件。

生产者和消费者彼此不知道对方，独立工作。生产者通过将消息发布到由事件代理操作的通道来发送事件通知，事件代理负责收集和路由消息到消费者。

10.1.1 理解事件驱动模型

事件驱动架构可以基于两种主要模型：

  • 发布/订阅（pub/sub） — 此模型基于订阅。生产者发布事件，这些事件被发送给所有订阅者进行消费。事件被接收后无法重放，因此新加入的消费者将无法获取过去的事件。

  • 事件流 — 在此模型中，事件被写入日志。生产者在事件发生时发布事件，所有事件按顺序存储。消费者不订阅它们，但可以从事件流的任何部分读取。在此模型中，事件可以重放。客户端可以随时加入并接收所有过去的事件。

10.1.2 使用 pub/sub 模型

在 Polar Bookshop 系统中，我们需要实现事件驱动解决方案，允许不同应用程序异步通信，同时减少耦合。

需求： * 当订单被接受时，Order Service 应通知感兴趣的消费者 * 当订单被调度时，Dispatcher Service 应通知消费者，Order Service 应更新订单状态

这种类型的交互应该是异步的，可以使用 pub/sub 模型建模。

11.3 JWT 认证

JSON Web Token (JWT) 是一种开放标准（RFC 7519），定义了一种紧凑且自包含的方式，用于在各方之间安全地传输信息。

11.3.1 JWT 结构

JWT 由三部分组成：

  1. 头部（Header） — 包含令牌类型和签名算法
  2. 载荷（Payload） — 包含声明（claims）
  3. 签名（Signature） — 用于验证令牌

11.3.2 配置 JWT 资源服务器

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://your-auth-server.com
          jwk-set-uri: https://your-auth-server.com/.well-known/jwks.json

11.3.3 从 JWT 中提取用户信息

@RestController
public class UserController {

    @GetMapping("/user")
    public Map<String, Object> getUser(@AuthenticationPrincipal Jwt jwt) {
        Map<String, Object> user = new HashMap<>();
        user.put("sub", jwt.getSubject());
        user.put("email", jwt.getClaimAsString("email"));
        user.put("roles", jwt.getClaimAsStringList("roles"));
        return user;
    }
}

11.3.4 自定义 JWT 声明

@Configuration
public class JwtConfig {

    @Bean
    public JwtDecoder jwtDecoder() {
        NimbusJwtDecoder decoder = NimbusJwtDecoder
            .withJwkSetUri("https://your-auth-server.com/.well-known/jwks.json")
            .build();
        return decoder;
    }
}

JWT 认证是保护微服务架构中 API 的常用方式，因为它无状态且易于在服务之间传递。

    public OrderService(MeterRegistry registry) {

            .description("Total number of orders")

            .description("Order processing time")
            .register(registry);

15.1 CI/CD 流水线

15.1.1 理解 CI/CD

  • 持续交付（CD） — 自动化将通过所有测试阶段的应用程序部署到生产环境
  • 持续部署 — 自动化将通过所有测试阶段的应用程序部署到生产环境，无需人工干预

15.1.2 GitHub Actions 配置

name: CI/CD Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up JDK 17
        uses: actions/setup-java@v3

      - name: Run tests

    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Deploy to Kubernetes

16.1 Serverless 架构

Serverless 是一种云原生开发模型，允许开发人员构建和运行应用程序，而无需管理服务器。

16.1.1 Serverless 核心概念

Serverless 的主要特点：

  • 按需执行 — 代码只在需要时运行
  • 按使用付费 — 只为实际使用的计算资源付费
  • 自动扩缩容 — 根据负载自动扩展
  • 无服务器管理 — 云提供商管理基础设施

16.1.2 Serverless 平台

  • AWS Lambda — Amazon 的 Serverless 计算服务
  • Azure Functions — Microsoft 的 Serverless 平台
  • Google Cloud Functions — Google 的 Serverless 服务
  • Knative — Kubernetes 上的 Serverless 平台

16.1.3 Serverless 的优势

  • 降低运维成本
  • 提高开发效率
  • 自动扩展
  • 无需预置容量

16.1.4 Serverless 的局限

  • 冷启动延迟
  • 执行时间限制
  • 供应商锁定
  • 调试复杂性

Serverless 适合事件驱动的工作负载和微服务架构。

16.2 GraalVM 原生镜像

GraalVM 是一个高性能的多语言虚拟机，可以将 Java 应用程序编译为原生镜像，显著减少启动时间和内存占用。

16.2.1 理解原生镜像

原生镜像是一个自包含的可执行文件，包含应用程序和所有依赖项，不需要 JVM 即可运行。

优势： * 快速启动 — 毫秒级启动时间 * 低内存占用 — 更少的内存消耗 * 无需 JVM — 可以在没有 Java 运行时的环境中运行

16.2.2 使用 Spring Boot 构建原生镜像

使用 Gradle：

./gradlew bootBuildImage --builder=ghcr.io/graalvm/native-image:latest

使用 Maven：

mvn -Pnative spring-boot:build-image

16.2.3 配置原生镜像

<build>
    <plugins>
        <plugin>
            <groupId>org.graalvm.buildtools</groupId>
            <artifactId>native-maven-plugin</artifactId>
        </plugin>
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
            <configuration>
                <image>
                    <builder>paketobuildpacks/builder-jammy-java:latest</builder>
                </image>
            </configuration>
        </plugin>
    </plugins>
</build>

16.2.4 测试原生镜像

# 构建原生镜像
./mvnw -Pnative native:compile

# 运行原生镜像
./target/catalog-service

GraalVM 原生镜像特别适合 Serverless 和容器化部署。

16.3.4 自动扩缩容到零

Knative 可以在没有请求时自动将服务缩放为零，节省资源：

kind: Service
metadata:
  name: catalog-service
spec:
  template:
    metadata:
      annotations:
        autoscaling.knative.dev/minScale: "0"
        autoscaling.knative.dev/maxScale: "10"
    spec:
      containers:
        - image: ghcr.io/your-username/catalog-service:latest
