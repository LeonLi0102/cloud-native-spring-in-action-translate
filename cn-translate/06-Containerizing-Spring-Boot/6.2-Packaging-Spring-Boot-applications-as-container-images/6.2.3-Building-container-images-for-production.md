### 6.2.3 为生产构建容器镜像

Dockerfile 入门可能一开始并不难，但构建生产级镜像可能具有挑战性。在本节中，您将看到如何改进上一节中构建的镜像。

您将使用 Spring Boot 提供的分层 JAR 功能来构建更高效的镜像。然后考虑与容器镜像相关的重要安全方面。最后，我将讨论在容器化应用程序时选择 Dockerfile 和 Cloud Native Buildpacks 之间需要考虑的一些因素。

#### 性能

构建容器镜像时，您应该考虑构建时和运行时的性能。OCI 镜像的分层架构支持在构建镜像时缓存和重用未更改的层。容器注册表按层存储镜像，因此当您拉取新版本时，只下载更改的层。这在云环境中是一个很大的优势，考虑到您为所有应用程序实例节省的时间和带宽。

在上一节中，您将 Catalog Service 的独立 JAR 文件复制到镜像中的一个层中。结果，每当您更改应用程序中的某些内容时，整个层都必须重新构建。考虑这样一个场景：您只是向应用程序添加了一个新的 REST 端点。即使所有 Spring 库和依赖项都未更改，唯一的区别在于您自己的代码，您也必须重新构建整个层，因为所有内容都在一起。我们可以做得更好。Spring Boot 可以帮助我们。

将 uber-JAR 放入容器镜像中从来都不是高效的。JAR 工件是一个压缩归档文件，包含应用程序使用的所有依赖项、类和资源。所有这些文件都组织在 JAR 内的文件夹和子文件夹中。我们可以展开标准 JAR 工件，并将每个文件夹放在不同的容器镜像层上。从 2.3 版本开始，Spring Boot 通过引入一种将应用程序打包为 JAR 工件的新方式使这更加高效：分层 JAR 模式。从 Spring Boot 2.4 开始，这已成为默认模式，因此您不需要任何额外配置即可使用新功能。

使用分层 JAR 模式打包的应用程序由多个层组成，类似于容器镜像的工作方式。这个新功能非常适合构建更高效的镜像。使用新的 JAR 打包方式时，我们可以展开 JAR 工件，然后为每个 JAR 层创建一个不同的镜像层。目标是将您自己的类（更改更频繁的）与项目依赖项（更改不那么频繁的）放在不同的层上。

默认情况下，Spring Boot 应用程序打包为由以下层组成的 JAR 工件（从最低层开始）：

* **dependencies** — 项目添加的所有主要依赖项
* **spring-boot-loader** — Spring Boot 加载器组件使用的类
* **snapshot-dependencies** — 所有快照依赖项
* **application** — 应用程序类和资源

如果考虑之前添加新 REST 端点到现有应用程序的场景，容器化时只需要构建 application 层。此外，当您在生产环境中升级应用程序时，只需要将该新层下载到运行容器的节点，使升级更快更便宜（尤其是在按使用带宽计费的云平台上）。

让我们更新之前的 Dockerfile，使用分层 JAR 模式更高效地容器化 Catalog Service。使用这种新策略意味着需要做一些准备工作来将 JAR 文件复制到镜像中并将其展开为前面描述的四个层。我们不希望将原始 JAR 文件保留在镜像中，否则我们的优化计划将不起作用。Docker 为此提供了解决方案：多阶段构建。

我们将把工作分为两个阶段。在第一阶段，我们从 JAR 文件中提取层。第二阶段是我们将每个 JAR 层放入一个单独的镜像层。最终，第一阶段的结果被丢弃（包括原始 JAR 文件），而第二阶段将产生最终的容器镜像。

**代码清单 6.3 更高效的 Dockerfile，用于构建 Catalog Service 镜像**

```dockerfile
# 第一阶段的 OpenJDK 基础镜像
FROM eclipse-temurin:17 AS builder

WORKDIR workspace

# 构建参数，指定项目中应用程序 JAR 文件的位置路径
ARG JAR_FILE=build/libs/*.jar

# 将应用程序 JAR 文件从本地机器复制到镜像中的 "workspace" 文件夹
COPY ${JAR_FILE} catalog-service.jar

# 应用分层 JAR 模式从归档中提取层
RUN java -Djarmode=layertools -jar catalog-service.jar extract

# 第二阶段的 OpenJDK 基础镜像
FROM eclipse-temurin:17

WORKDIR workspace

# 将每个 JAR 层从第一阶段复制到第二阶段的 "workspace" 文件夹
COPY --from=builder workspace/dependencies/ ./
COPY --from=builder workspace/spring-boot-loader/ ./
COPY --from=builder workspace/snapshot-dependencies/ ./
COPY --from=builder workspace/application/ ./

# 使用 Spring Boot Launcher 从层而不是 uber-JAR 启动应用程序
ENTRYPOINT ["java", "org.springframework.boot.loader.JarLauncher"]
```

> 注意：如果您想更改 JAR 文件中层的配置怎么办？与往常一样，Spring Boot 提供了合理的默认值，但您可以自定义它以适应您的需求。也许您的项目有一些内部共享依赖项，您可能想将它们放在单独的层中，因为它们比第三方依赖项更改得更频繁。您可以通过 Spring Boot Gradle 或 Maven 插件来做到这一点。有关更多信息，请参阅 Spring Boot 文档：[https://spring.io/projects/spring-boot](https://spring.io/projects/spring-boot)。

构建和运行容器的过程与之前相同，但现在镜像更高效，在构建和执行时都经过了优化。然而，它仍然没有准备好用于生产。安全性呢？这就是下一节的主题。

#### 安全性

安全性是一个关键方面，但经常被刚接触 Docker 和容器化的人所低估。您应该意识到，容器默认使用 root 用户运行，这可能让它们获得对 Docker 主机的 root 访问权限。您可以通过创建一个非特权用户并使用它来运行 Dockerfile 中定义的入口点进程来降低风险，遵循最小权限原则。

考虑您为 Catalog Service 编写的 Dockerfile。您可以通过添加新步骤来创建一个新的非 root 用户来运行应用程序，从而改进它。

**代码清单 6.4 更安全的 Dockerfile，用于构建 Catalog Service 镜像**

```dockerfile
FROM eclipse-temurin:17 AS builder
WORKDIR workspace
ARG JAR_FILE=build/libs/*.jar
COPY ${JAR_FILE} catalog-service.jar
RUN java -Djarmode=layertools -jar catalog-service.jar extract

FROM eclipse-temurin:17
# 创建一个 "spring" 用户
RUN useradd spring
# 配置 "spring" 为当前用户
USER spring

WORKDIR workspace

COPY --from=builder workspace/dependencies/ ./
COPY --from=builder workspace/spring-boot-loader/ ./
COPY --from=builder workspace/snapshot-dependencies/ ./
COPY --from=builder workspace/application/ ./

ENTRYPOINT ["java", "org.springframework.boot.loader.JarLauncher"]
```

如前所述，您永远不应在容器镜像中存储密码或密钥等机密信息。即使它们在上一层被删除，它们仍将完整地保留在原始层中，并且很容易被访问。

最后，在 Dockerfile 中使用最新的基础镜像和库也很关键。扫描容器镜像中的漏洞是一项应该在部署管道中采纳和自动化的最佳实践。在第 3 章中，您学习了如何使用 grype 扫描代码库中的漏洞。现在我们还将使用它来扫描容器镜像。

使用更新后的 Dockerfile，为 Catalog Service 构建一个新的容器镜像。打开终端窗口，导航到 Catalog Service 根文件夹，运行此命令（不要忘记最后的点）：

```bash
$ docker build -t catalog-service .
```

接下来，使用 grype 检查新创建的镜像是否包含任何漏洞：

```bash
$ grype catalog-service
```

在本节中，我提到了构建生产级容器镜像时应考虑的几个重要方面，但还有更多内容需要涵盖。是否有另一种构建生产级容器镜像的方法？下一节介绍了一个不同的选择。
