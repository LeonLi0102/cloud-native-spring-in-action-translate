### 4.3.3 使配置服务器更具韧性

Config Service 可能成为系统中的单点故障。如果所有应用程序都依赖它来获取配置数据，您需要确保它具有高可用性。实现这一目标的第一步是在生产环境中部署多个 Config Service 实例。如果其中一个因某种原因停止工作，另一个副本可以提供所需的配置。在第 7 章中，您将学习更多关于扩展应用程序以及如何在 Kubernetes 中实现这一点的内容。

然而，仅扩展 Config Service 是不够的。由于它使用远程 Git 仓库作为配置数据后端，您还需要使该交互更具韧性。首先，您可以定义一个超时时间，以防止配置服务器等待太长时间来建立与远程仓库的连接。您可以通过 `spring.cloud.config.server.git.timeout` 属性来实现。

Spring Cloud Config 的实现是在首次请求配置数据时将远程仓库克隆到本地。我建议使用 `spring.cloud.config.server.git.clone-on-start` 属性，以便在启动时进行仓库克隆。虽然这会使启动阶段稍慢，但如果与远程仓库通信存在困难，它能让您的部署更快失败，而不是等到第一个请求才发现问题。此外，它使客户端的第一次请求更快。

仓库的本地副本提高了配置服务器的容错能力，因为它确保即使与远程仓库的通信暂时失败（例如 GitHub 宕机或网络问题），也能向客户端应用程序返回配置数据。然而，如果配置服务器尚未在本地克隆仓库，就没有回退机制。这就是为什么最好在启动时快速失败并立即调查问题。

当成功创建仓库的本地副本时，本地仓库可能会独立于远程仓库被更改。您可以通过设置 `spring.cloud.config.server.git.force-pull` 属性来确保配置服务器始终使用远程仓库中定义的相同数据，这样 whenever 本地副本损坏时会拉取新副本，并丢弃任何本地更改。默认情况下，本地仓库克隆在一个随机名称的文件夹中。如果需要，您可以通过 `spring.cloud.config.server.git.basedir` 属性控制克隆位置。对于 Config Service，我们将依赖默认行为。

您可以更新 Config Service 应用程序的 `application.yml` 文件，使其对影响与代码仓库服务（在本例中为 GitHub）交互的故障更具韧性。

**代码清单 4.13 使 Config Service 更具韧性**

```yaml
spring:
 application:
 name: config-service
 cloud:
 config:
 server:
 git:
 uri: <your-config-repo-github-url>
 default-label: main
 timeout: 5 # 与远程仓库建立连接的时间限制
 clone-on-start: true # 在启动时本地克隆远程仓库
 force-pull: true # 强制拉取远程仓库并丢弃任何本地更改
```
