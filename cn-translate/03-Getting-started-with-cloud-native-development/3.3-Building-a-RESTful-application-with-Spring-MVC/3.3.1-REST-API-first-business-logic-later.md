### 3.3.1 REST API 优先，业务逻辑在后

API 优先设计的前提是您已经定义了需求，所以让我们从需求开始。Catalog Service 将负责支持以下用例：

* 查看目录中的图书列表。
* 按国际标准书号（ISBN）搜索图书。
* 向目录中添加一本新书。
* 编辑现有图书的信息。
* 从目录中移除一本书。

换句话说，应用应该提供一个 API 来对图书执行 CRUD 操作。格式将遵循应用于 HTTP 的 REST 风格。有多种方式可以设计 API 来满足这些用例。在本章中，我们将使用表 3.1 中描述的方法。

**表 3.1 Catalog Service 将暴露的 REST API 规范**

| 端点 | HTTP 方法 | 请求体 | 状态码 | 响应体 | 描述 |
|------|-----------|--------|--------|--------|------|
| `/books` | GET | | 200 | Book[] | 获取目录中所有图书 |
| `/books` | POST | Book | 201 | Book | 向目录中添加新书 |
| `/books` | POST | Book | 422 | | 具有相同 ISBN 的图书已存在 |
| `/books/{isbn}` | GET | | 200 | Book | 获取指定 ISBN 的图书 |
| `/books/{isbn}` | GET | | 404 | | 指定 ISBN 的图书不存在 |
| `/books/{isbn}` | PUT | Book | 200 | Book | 更新指定 ISBN 的图书 |
| `/books/{isbn}` | PUT | Book | 201 | Book | 创建指定 ISBN 的图书 |
| `/books/{isbn}` | DELETE | | 204 | | 删除指定 ISBN 的图书 |

> **文档化 API**
>
> 当您遵循 API 优先方法时，文档化 API 是一项重要任务。在 Spring 生态系统中，有两个主要选择：
>
> * Spring 提供了 Spring REST Docs 项目（[https://spring.io/projects/spring-restdocs](https://spring.io/projects/spring-restdocs)），帮助您通过测试驱动开发（TDD）来文档化 REST API，产生高质量且可维护的文档。生成的文档面向人，依赖 Asciidoc 或 Markdown 等格式。如果您还想获得 OpenAPI 表示，可以查看 restdocs-api-spec 社区驱动项目，为 Spring REST Docs 添加 OpenAPI 支持（[https://github.com/ePages-de/restdocs-api-spec](https://github.com/ePages-de/restdocs-api-spec)）。
> * springdoc-openapi 社区驱动项目帮助按照 OpenAPI 3 格式自动生成 API 文档（[https://springdoc.org](https://springdoc.org)）。

契约通过 REST API 建立，让我们继续看业务逻辑。解决方案围绕三个概念：

* **实体（Entity）** —— 实体代表领域中的名词，例如"图书"。
* **服务（Service）** —— 服务定义领域的用例。例如，"向目录中添加一本书"。
* **仓库（Repository）** —— 仓库是一种抽象，让领域层独立于数据源来访问数据。

让我们从领域实体开始。

#### 定义领域实体

表 3.1 中定义的 REST API 应该使操作图书成为可能。这就是领域实体。在 Catalog Service 项目中，创建一个新的 `com.polarbookshop.catalogservice.domain` 包用于业务逻辑，并创建一个 `Book` Java record 来表示领域实体。

**代码清单 3.4 使用 Book record 定义应用的领域实体**

```java
package com.polarbookshop.catalogservice.domain;

public record Book (
 String isbn, // 唯一标识一本书
 String title,
 String author,
 Double price
) {}
```

领域模型被实现为 record —— 一种不可变对象。

#### 实现用例

应用需求列举的用例可以在一个 `@Service` 类中实现。在 `com.polarbookshop.catalogservice.domain` 包中，创建一个 `BookService` 类，如下面的代码清单所示。该服务依赖于一些您稍后将创建的类。

**代码清单 3.5 实现应用的用例**

```java
package com.polarbookshop.catalogservice.domain;

import org.springframework.stereotype.Service;

@Service // 标记类为由 Spring 管理的服务
public class BookService {

 private final BookRepository bookRepository;

 public BookService(BookRepository bookRepository) {
 // BookRepository 通过构造器自动注入
 this.bookRepository = bookRepository;
 }

 public Iterable<Book> viewBookList() {
 return bookRepository.findAll();
 }

 public Book viewBookDetails(String isbn) {
 return bookRepository.findByIsbn(isbn)
 // 当尝试查看不存在的图书时，抛出专用异常
 .orElseThrow(() -> new BookNotFoundException(isbn));
 }

 public Book addBookToCatalog(Book book) {
 if (bookRepository.existsByIsbn(book.isbn())) {
 // 当多次添加同一本书时，抛出专用异常
 throw new BookAlreadyExistsException(book.isbn());
 }
 return bookRepository.save(book);
 }

 public void removeBookFromCatalog(String isbn) {
 bookRepository.deleteByIsbn(isbn);
 }

 public Book editBookDetails(String isbn, Book book) {
 return bookRepository.findByIsbn(isbn)
 .map(existingBook -> {
 // 编辑图书时，除 ISBN 外的所有字段都可以更新，因为 ISBN 是实体标识符
 var bookToUpdate = new Book(
 existingBook.isbn(),
 book.title(),
 book.author(),
 book.price()
 );
 return bookRepository.save(bookToUpdate);
 })
 // 当更改不在目录中的图书详情时，创建一本新书
 .orElseGet(() -> addBookToCatalog(book));
 }
}
```

> **注意** Spring Framework 提供两种依赖注入方式：基于构造器和基于 setter。我们将在所有生产代码中使用基于构造器的依赖注入，正如 Spring 团队所倡导的，因为它确保所需依赖总是完全初始化且永不为 null。此外，它鼓励构建不可变对象并提高可测试性。更多信息请参阅 Spring Framework 文档（[https://spring.io/projects/spring-framework](https://spring.io/projects/spring-framework)）。

#### 使用仓库抽象进行数据访问

`BookService` 类依赖一个 `BookRepository` 对象来检索和保存图书。领域层应该不知道数据是如何持久化的，因此 `BookRepository` 应该是一个接口，以将抽象与实际实现解耦。在 `com.polarbookshop.catalogservice.domain` 包中创建一个 `BookRepository` 接口来定义访问图书数据的抽象。

**代码清单 3.6 领域层用于访问数据的抽象**

```java
package com.polarbookshop.catalogservice.domain;

import java.util.Optional;

public interface BookRepository {
 Iterable<Book> findAll();
 Optional<Book> findByIsbn(String isbn);
 boolean existsByIsbn(String isbn);
 Book save(Book book);
 void deleteByIsbn(String isbn);
}
```

虽然仓库接口属于领域层，但其实现属于持久化层。我们将在第 5 章使用关系型数据库添加数据持久化层。现在，添加一个简单的内存映射来检索和保存图书就够了。您可以在 `InMemoryBookRepository` 类中定义实现，位于新的 `com.polarbookshop.catalogservice.persistence` 包中。

**代码清单 3.7 BookRepository 接口的内存实现**

```java
package com.polarbookshop.catalogservice.persistence;

import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import com.polarbookshop.catalogservice.domain.Book;
import com.polarbookshop.catalogservice.domain.BookRepository;
import org.springframework.stereotype.Repository;

@Repository // 标记类为由 Spring 管理的仓库
public class InMemoryBookRepository implements BookRepository {

 // 用于测试目的的内存映射存储图书
 private static final Map<String, Book> books = new ConcurrentHashMap<>();

 @Override
 public Iterable<Book> findAll() {
 return books.values();
 }

 @Override
 public Optional<Book> findByIsbn(String isbn) {
 return existsByIsbn(isbn) ? Optional.of(books.get(isbn)) : Optional.empty();
 }

 @Override
 public boolean existsByIsbn(String isbn) {
 return books.get(isbn) != null;
 }

 @Override
 public Book save(Book book) {
 books.put(book.isbn(), book);
 return book;
 }

 @Override
 public void deleteByIsbn(String isbn) {
 books.remove(isbn);
 }
}
```

#### 使用异常在领域层中发出错误信号

让我们通过实现在代码清单 3.5 中使用的两个异常来完成 Catalog Service 的业务逻辑。

`BookAlreadyExistsException` 是一个运行时异常，当我们尝试将一本已存在的图书添加到目录时抛出。它防止目录中出现重复条目。

**代码清单 3.8 添加已存在图书时抛出的异常**

```java
package com.polarbookshop.catalogservice.domain;

public class BookAlreadyExistsException extends RuntimeException {
 public BookAlreadyExistsException(String isbn) {
 super("A book with ISBN " + isbn + " already exists.");
 }
}
```

`BookNotFoundException` 是一个运行时异常，当我们尝试获取目录中不存在的图书时抛出。

**代码清单 3.9 找不到图书时抛出的异常**

```java
package com.polarbookshop.catalogservice.domain;

public class BookNotFoundException extends RuntimeException {
 public BookNotFoundException(String isbn) {
 super("The book with ISBN " + isbn + " was not found.");
 }
}
```

这就完成了 Catalog Service 的业务逻辑。它相对简单，但建议不要受数据持久化方式或与客户端交换方式的影响。业务逻辑应该独立于其他一切，包括 API。如果您对这个主题感兴趣，我建议探索领域驱动设计和六边形架构的概念。
