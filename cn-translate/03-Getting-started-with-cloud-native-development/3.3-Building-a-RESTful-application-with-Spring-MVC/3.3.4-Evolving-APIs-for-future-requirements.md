### 3.3.4 为未来需求演进 API

在分布式系统中，我们需要一个计划来演进 API，以便不破坏其他应用的功能。这是一项具有挑战性的任务，因为我们想要独立的应用，但它们可能正是为了向其他应用提供服务而存在的，因此我们在独立于客户端可以进行的更改数量上受到了一定限制。

最好的方法是对 API 进行向后兼容的更改。例如，我们可以向 `Book` 对象添加一个可选字段，而不会影响 Catalog Service 应用的客户端。

有时，破坏性更改是必要的。在这种情况下，您可以使用 API 版本控制。例如，如果您决定对 Catalog Service 应用的 REST API 进行破坏性更改，您可以为端点引入一个版本控制系统。版本可以是端点本身的一部分，如 `/v2/books`。或者它可以作为 HTTP 头指定。这种系统有助于防止现有客户端被破坏，但它们迟早必须更新其接口以匹配新的 API 版本，这意味着需要协调。

另一种方法侧重于使 REST API 客户端尽可能对 API 更改具有弹性。解决方案是使用 REST 架构的超媒体方面，正如 Roy Fielding 博士在其博士论文《架构风格与基于网络的软件架构设计》中所述（[www.ics.uci.edu/~fielding/pubs/dissertation/top.htm](http://www.ics.uci.edu/~fielding/pubs/dissertation/top.htm)）。REST API 可以返回请求的对象以及有关下一步去哪里的信息和执行相关操作的链接。这个特性的美妙之处在于，链接只在有意义跟随它们时才显示，提供了关于何时去的信息。

这种超媒体方面也称为 HATEOAS（Hypermedia as the Engine of Application State，超媒体作为应用状态的引擎），根据 Richardson 成熟度模型，它代表了 API 成熟度的最高级别。Spring 提供了 Spring HATEOAS 项目来为 REST API 添加超媒体支持。我在本书中不会使用它，但我鼓励您查看该项目的在线文档：[https://spring.io/projects/spring-hateoas](https://spring.io/projects/spring-hateoas)。

这些考量结束了我们关于使用 Spring 构建 RESTful 应用的讨论。在下一节中，您将看到如何编写自动化测试来验证应用的行为。
