## 14.3 使用 Kustomize 管理配置

Kubernetes 提供了许多用于运行云原生应用的强大特性。不过，它要求编写多个 YAML 清单，这些清单在实际场景中有时显得冗余且难以管理。在收集了部署应用所需的多个清单之后，我们还面临额外的挑战。如何根据环境修改 ConfigMap 中的值？如何修改容器镜像版本？Secrets 和卷又该怎么办？能否更新健康检查探针的配置？

近年来，人们引入了许多工具来改进我们在 Kubernetes 中配置和部署工作负载的方式。对于 Polar Bookshop 项目，我们希望有一个能让我们把多个 Kubernetes 清单作为一个整体处理、并根据应用部署环境定制部分配置的工具。

Kustomize（https://kustomize.io）是一个声明式工具，通过分层（layering）方法帮助为不同环境配置部署。它生成标准的 Kubernetes 清单，并且内置于 Kubernetes CLI（kubectl）中，因此你无需额外安装什么东西。

> 注意：其他流行的 Kubernetes 部署配置管理选项还有 Carvel 套件中的 ytt（https://carvel.dev/ytt）和 Helm（https://helm.sh）。

本节将向你展示 Kustomize 提供的核心功能。首先你会看到如何组合相关的 Kubernetes 清单并作为一个整体处理。然后我将展示 Kustomize 如何基于属性文件为你生成一个 ConfigMap。最后，我会带领你完成一系列定制操作，我们将把这些定制应用到 base 清单上，然后再部署到 staging 环境的负载。下一章将进一步扩展这些内容，并涵盖生产场景。

在继续之前，请确保你的本地 minikube 集群仍在运行，并且 Polar Bookshop 的支撑服务已正确部署。如果没有，请在 polar-deployment 项目中运行 `./create-cluster.sh`。

> 注意：平台服务只在集群内部暴露。如果你想从本地机器访问它们，可以使用你在第 7 章学到的端口转发功能。你既可以借助 Octant 提供的 GUI，也可以使用 CLI（`kubectl port-forward service/polar-postgres 5432:5432`）。

现在，既然所有支撑服务都已可用，让我们看看如何用 Kustomize 管理和配置一个 Spring Boot 应用。

### 14.3.1 使用 Kustomize 管理和配置 Spring Boot 应用

到目前为止，我们都是通过应用多个 Kubernetes 清单来把应用部署到 Kubernetes。例如，部署 Catalog Service 需要把 ConfigMap、Deployment 和 Service 清单应用到集群。使用 Kustomize 时，第一步是把相关清单组合起来，这样我们就可以把它们作为一个整体处理。Kustomize 通过一个 Kustomization 资源实现这一点。最终，我们希望让 Kustomize 帮助我们管理、处理和生成 Kubernetes 清单。

让我们看看它是如何工作的。打开你的 Catalog Service 项目（`catalog-service`），在 `k8s` 文件夹内创建一个 `kustomization.yml` 文件。它将是 Kustomize 的入口点。

我们首先要让 Kustomize 知道，它应该以哪些 Kubernetes 清单作为未来定制的基础。目前，我们将使用现有的 Deployment 和 Service 清单。

**清单 14.4 为 Kustomize 定义基础 Kubernetes 清单**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yml
  - service.yml
```

`apiVersion`：Kustomize 的 API 版本；`kind`：清单定义的资源类型；`resources`：Kustomize 应管理和处理的 Kubernetes 清单。

你可能想知道为什么我们没有包含 ConfigMap。很高兴你问这个问题！我们本可以把本章前面创建的 `configmap.yml` 文件包含进来，但 Kustomize 提供了一种更好的方式。与其直接引用一个 ConfigMap，我们可以提供一个属性文件，让 Kustomize 用它来生成一个 ConfigMap。让我们看看如何实现。

首先，把我们之前创建的 ConfigMap 的正文（`configmap.yml`）移动到一个新的 `application.yml` 文件（位于 `k8s` 文件夹内）。

**清单 14.5 通过 ConfigMap 提供的配置属性**

```yaml
polar:
  greeting: Welcome to the book catalog from Kubernetes!
spring:
  datasource:
    url: jdbc:postgresql://polar-postgres/polardb_catalog
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://polar-keycloak/realms/PolarBookshop
```

然后删除 `configmap.yml` 文件，我们不再需要它了。最后，更新 `kustomization.yml` 文件，让它从我们刚创建的 `application.yml` 文件为起点生成一个 `catalog-config` ConfigMap。

**清单 14.6 让 Kustomize 从属性文件生成 ConfigMap**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - deployment.yml
  - service.yml
configMapGenerator:
  - name: catalog-config
    files:
      - application.yml
    options:
      labels:
        app: catalog-service
```

`configMapGenerator`：包含用于生成 ConfigMap 信息的部分；`files: - application.yml`：使用属性文件作为 ConfigMap 的数据源；`options.labels`：定义要分配给生成的 ConfigMap 的标签。

> 注意：以类似的方式，Kustomize 也能从字面值或文件生成 Secrets。

让我们暂停片刻，验证到目前为止所做的工作是否正确。你的本地集群应该已经拥有你的 Catalog Service 容器镜像。如果没有，请构建容器镜像（`./gradlew bootBuildImage`）并加载到 minikube（`minikube image load catalog-service --profile polar`）。

接下来，打开终端窗口，导航到 Catalog Service 项目（`catalog-service`），使用熟悉的 Kubernetes CLI 部署应用。应用标准 Kubernetes 清单时，我们使用 `-f` 标志。应用 Kustomization 时，使用 `-k` 标志：

```bash
$ kubectl apply -k k8s
```

最终结果应该与之前直接应用 Kubernetes 清单时一样，只是这次 Kustomize 通过一个 Kustomization 资源处理了一切。

为完成验证，使用端口转发策略把 Catalog Service 应用暴露到你的本地机器（`kubectl port-forward service/catalog-service 9001:80`）。然后打开一个新的终端窗口，确认根端点返回的是通过 Kustomize 生成的 ConfigMap 所配置的消息：

```bash
$ http :9001/
Welcome to the book catalog from Kubernetes!
```

Kustomize 生成的 ConfigMaps 和 Secrets 在部署时会带上一个唯一后缀（hash）。你可以用下面的命令验证分配给 catalog-config ConfigMap 的实际名称：

```bash
$ kubectl get cm -l app=catalog-service
NAME                     DATA   AGE
catalog-config-btcmff5d78   1      7m58s
```

每当更新生成器（generator）的输入时，Kustomize 都会创建一个带有不同 hash 的新清单，这会触发使用这些更新后的 ConfigMaps 或 Secrets 卷的容器进行滚动重启。这是一种非常便捷的方式，无需实现或配置任何额外组件，就能实现自动化的配置刷新。

让我们验证一下事实是否如此。首先，更新用于 Kustomize 生成 ConfigMap 的 `application.yml` 文件中 `polar.greeting` 属性的值。

**清单 14.7 更新 ConfigMap 生成器的配置输入**

```yaml
polar:
  greeting: Welcome to the book catalog from a development Kubernetes environment!
...
```

然后再次应用 Kustomization（`kubectl apply -k k8s`）。Kustomize 会生成一个后缀 hash 不同的新 ConfigMap，从而触发所有 Catalog Service 实例的滚动重启。本例中只运行一个实例。在生产环境中实例会更多。实例一个个重启，意味着更新期间零停机，这正是我们在云中追求的目标。Catalog Service 的根端点现在应该返回新的消息：

```bash
$ http :9001/
Welcome to the book catalog from a Kubernetes environment!
```

如果你好奇，可以把这与不使用 Kustomize 时更新 ConfigMap 会发生什么做个对比。Kubernetes 会更新挂载到 Catalog Service 容器的卷，但应用不会被重启，并且仍会返回旧值。

> 注意：根据你的需求，你可能需要避免滚动重启，并让应用在运行时重新加载配置。在这种情况下，你可以用 `disableNameSuffixHash: true` 生成器选项禁用 hash 后缀策略，也许可以借助 Spring Cloud Kubernetes Configuration Watcher 之类的方案在 ConfigMap 或 Secret 发生变化时通知应用。

完成了 Kustomize 设置实验之后，你可以停止端口转发进程（Ctrl-C）并卸载 Catalog Service（`kubectl delete -k k8s`）。

由于我们从普通的 Kubernetes 清单切换到了 Kustomize，我们还需要更新一些东西。在第 7 章中，我们使用 Tilt 在本地 Kubernetes 开发时获得更好的开发工作流。Tilt 支持 Kustomize，因此我们可以配置它通过 Kustomization 资源部署应用，而不是通过普通 Kubernetes 清单。请更新 Catalog Service 项目中的 Tiltfile，如下所示。

**清单 14.8 配置 Tilt 用 Kustomize 部署 Catalog Service**

```python
custom_build(
    ref = 'catalog-service',
    command = './gradlew bootBuildImage --imageName $EXPECTED_REF',
    deps = ['build.gradle', 'src']
)
k8s_yaml(kustomize('k8s'))

k8s_resource('catalog_service', port_forwards=['9001'])
```

从位于 k8s 文件夹的 Kustomization 运行应用。

最后，我们需要更新 Catalog Service 提交阶段（commit stage）工作流中的 manifest 校验步骤，否则下次我们向 GitHub 推送变更时它会失败。在你的 Catalog Service 项目中打开 `commit-stage.yml` 文件（`.github/workflows`），按下面所示进行更新。

**清单 14.9 使用 Kubeval 校验 Kustomize 生成的清单**

```raku
name: Commit Stage
on: push
...
jobs:
  build:
    name: Build and Test
    ...
    steps:
      ...
      - name: Validate Kubernetes manifests
        uses: stefanprodan/kube-tools@v1
        with:
          kubectl: 1.24.3

            kustomize build k8s | kubeval --strict -
```

用 Kustomize 生成清单，然后用 Kubeval 校验它们。

到目前为止，我们从 Kustomize 获得的最大收益，是当 ConfigMap 或 Secret 被更新时应用自动滚动重启的能力。在下一节中，你将进一步了解 Kustomize 及其管理不同环境的不同 Kubernetes 配置的强力功能。

### 14.3.2 使用 Kustomize 管理多环境的 Kubernetes 配置

在开发过程中，我们遵循 15-Factor 方法论，为应用的每个可能在不同环境部署间变化的部分外部化配置。你看到了如何使用属性文件、环境变量、配置服务策略、ConfigMaps。我还展示了如何使用 Spring profiles，根据部署环境定制应用配置。现在我们需要更进一步，定义一种策略，根据应用的部署位置来定制整个部署配置。

在上一节，你学会了如何通过一个 Kustomization 资源把多个 Kubernetes 清单组合并处理。针对每个环境，我们都可以通过 patches，在这些基础清单之上应用修改或附加配置。你在本节看到的操作全部是在不修改应用源代码的情况下完成的，使用的还是之前产出的相同发布工件。这是一个相当强大的概念，也是云原生应用的主要特性之一。

Kustomize 配置定制的方法基于 base 和 overlay 的概念。我们在 Catalog Service 项目中创建的 `k8s` 文件夹可以看作一个 base：一个包含 `kustomization.yml` 文件的目录，它把多个 Kubernetes 清单和增强整合起来。overlay 则是相对于一个或多个 base 定义定制，并把它们组合起来。从一个 base 开始，你可以为每个部署环境（如开发、测试、staging、生产）指定一个 overlay。

如图 14.3 所示，每个 Kustomization 都包含一个 `kustomization.yml` 文件。多个 Deployment、Service、ConfigMaps 等 Kubernetes 资源会被 base 整合。Kustomize base 可以支撑各个环境的 futures 定制化（overlays）。

（说明：为便于阅读，此处把 lorem 的文字替换为图 14.3 的描述。）

**图 14.3** Kustomize base 可以作为根据不同部署环境进行进一步定制（overlays）的基石。

base 由多个 Kubernetes 清单（deployment.yml、service.yml、configmap.yml）组成，打包到 kustomization.yml 结构里。而 staging overlay 使用 base 的部署清单（patch-a.yml、patch-b.yml）再叠加补丁。production overlay 则用 patch-a.yml、patch-b.yml 之外，还可以引用 patch-x、patch-y、patch-z。

具体来说，base 并不知道有哪些 overlay 引用它，因此完全独立于它们。overlay 则把 base 作为基座，通过 patches 提供额外配置。

您可以把 base 和 overlay 定义在同一个仓库，也可以放在不同的仓库。对于 Polar Bookshop 系统，我们将把应用项目中的 `k8s` 文件夹作为 base，在 polar-deployment 仓库中定义 overlays。和你在第 3 章学到的应用代码仓库类似，你可以决定是否把某个应用的部署配置与应用放在同一个仓库。我决定放在单独的仓库，原因如下：

- 它使得在一个地方集中控制所有系统组件的部署成为可能。
- 在向生产环境部署之前，它允许进行有针对性的版本控制、审计和合规检查全部通过。
- 它适配 GitOps 方法，其中交付和部署任务被解耦。

图 14.4 展示了在 Catalog Service 这一具体例子里，Kustomize 清单如何通过 base 与 overlays 在两个独立的仓库中组织。base（目录内 `catalog-service/k8s`）和 overlays（`polar-deployment/applications/catalog-service/` 的 staging、production）引用关系。

**图 14.4** Kustomize base 和 overlays 可以存放在同一个仓库，也可以分别在两个仓库。overlays 可用来为不同环境定制部署。

你需要决定的另一件事是，把 base 的 Kubernetes 清单与应用源代码放在一起，还是放到部署仓库。对于 Polar Bookshop 示例，我决定采用第一种方案，这与我们对默认配置属性所做的处理类似。这么做的好处之一是，在开发期间让每个应用方便地在本地 Kubernetes 集群中运行，无论是直接运行还是使用 Tilt。不同的方案都可以根据你的需要选用。在实际项目中两者都成立，也都有应用。

您应该已经注意到，我在前面实验截图的正确性有多处依赖前文的文字说明。而对照全书约定，图片只需要保留图号以及位置，不需要精确重绘。

#### Patches 与 Templates

Kustomize 配置定制的方法基于应用补丁（patches）。这与 Helm（https://helm.sh）的工作方式截然相反。Helm 要求你对清单中想要改变的部分进行完全堆叠模板（这会计算出无效的 YAML）。之后，你可以为每个这些模板提供不同的值。如果一个字段没有模板化，你就无法继承它的值。正因为如此，把 Helm 和 Kustomize 串联起来使用并不罕见，可以互相弥补对方的不足。这两种方法都各有利弊。

在本书中，我决定使用 Kustomize，因为它内置于 Kubernetes CLI，与有效的 YAML 文件兼容，而且是纯粹的声明式。Helm 功能更强大，还能处理 Kubernetes 不支持多的复杂应用发布和升级。另一方面，它学习曲线陡峭，模板方案有一些缺陷，而且不是声明式的。

另一个选择是 Carvel 套件中的 ytt（https://carvel.dev/ytt）。它提供卓越的体验，同时支持 patches 和 templates，与有效 YAML 文件兼容，其模板策略也更清晰。熟悉 Helm 比 Kustomize 需要花更多工夫，但很值得。因为它把 YAML 当作核心支持项，所以 ytt 可以用于配置和定制任何 YAML 文件，甚至能在 Kubernetes 之外使用。你使用 GitHub Actions 工作流吗？Ansible playbooks？Jenkins pipelines？在这些所有场景中都可以用起来。

让我们考虑一下 Catalog Service。我们已经有了 base 部署配置，并且用 Kustomize 组合好了。它位于项目仓库的 `k8s` 文件夹中。现在让我们定义一个 overlay 来定制 staging 环境的部署。

### 14.3.3 定义 staging 环境的配置 overlay

在前面的章节中，我们用 Kustomize 管理 Catalog Service 在本地开发环境中的配置。那些清单将构成声明式/在不同环境中以 overlays 形式进行多种定制的基础。由于我们要在举报仓库中定义 overlays，Applications 仓库中的 Catalog Service 清单必须位于 main 分支之上。如果你还没有把对 Catalog Service 项目的所有改动推送到 GitHub 下的远程仓库，请现在发布。

> 注意：正如我在第 2 章中解释的那样，我期望你为系统的每个项目创建独立的 GitHub 仓库。在本章中，我们处理 `polar-deployment` 和 `catalog-service` 仓库，但你也应该在 edge-service、order-service 和 dispatcher-service 等项目上建立仓库。

正如预想的那样，我们会把任何配置 overlay 存放在 polar-deployment 仓库中。从现在起，我们将为 staging 环境定义一个 overlay，下一章将覆盖 production。

继续进入，在 polar-deployment 仓库中创建一个新的 `kubernetes/applications` 文件夹。我们使用该文件夹保存所有 Polar Bookshop 应用中不同的定制。在新创建的路径中，添加一个 `catalog-service` 文件夹，里面包含 Catalog Service 在不同环境部署所需的 overlay。特别是，我们将准备在 staging 的部署，所以为 Catalog Service 创建一个 "staging" 文件夹。

任何定制（base 或 overlay）都需要一个 `kustomization.yml` 文件。让我们为 Catalog Service 的 staging overlay 创建一个（`polar-deployment/kubernetes/applications/catalog-service/staging`）。第一件要配置的事情是对 base 清单的引用。

如果你跟着到现在，你将把 Catalog Service 的源代码保留在 GitHub 的 catalog-service 仓库中。对远程 base 的引用需要指向包含 `kustomization.yml` 文件的文件夹，就我们的案例而言是 `k8s`。另外，我们应该引用特定版本的 tag 或 digest，便于跟踪我们想部署的版本。我们将在下一章讨论版本策略和版本发布细节，现在就简简单单地指向基础分支 `main` 即可。最终工具地址应形如 `github.com/<your_github_username>/catalog-service/k8s?ref=main` 。例如，在我的情况下，会是 `github.com/polarbookshop/catalog-service/k8s?ref=main`。

**清单 14.10 在远程 base 之上定义 staging overlay**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - github.com/<your_github_username>/catalog-service/k8s?ref=
```

使用你在 GitHub 的 Catalog Service 仓库中的清单作为进一步定制的 base。

> 注意：我假设你创建的 GitHub 仓库都是公开的。如果不是，请进入 GitHub 上对应的仓库页面，登录仓库并打开 Settings 部分。然后滚动到设置页面底部，通过点击 Change Visibility 按钮可见并公开 packages。

现在我们可以用 CLI 从 staging overlay 部署 Catalog Service 了，但效果会和使用 base 完全一致。让我们开始针对 staging 部署应用一些定制化内容。

### 14.3.4 定制环境变量

我们可在 staging 要添加的个性化第一种定制是激活根环境变量，比如设置 Catalog Service 的 Spring profile 为 staging。大多数定制都可以通过 patch 以合并策略来实现。正如 branch 切换可以合并不同 branch 的变更，Kustomize 也能将来自不同 Kustomization 文件的变更合并并生成最终的 Kubernetes 清单。

定义 Kustomize patch 的黄金法则是保持小且集中。为扩展支持环境变量，在 Catalog Service 的 `kubernetes/applications/catalog-service/staging` 目录创建 `patch-env.yml` 文件。我们需要提供一些上下文信息，以便 Kustomize 判断补丁应该应用到哪以及如何处理合并。当补丁针对容器进行定制时，Kustomize 要求我们指定 Kubernetes 资源（如上，是 Deployment）和容器的名称。这种定制叫 strategic merge patch。

**清单 14.11 定制环境变量的补丁**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-service
spec:
  template:
    spec:
      containers:
        - name: catalog-service
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: staging
```

定义要激活的 Spring profiles。

接下来我们需要口算 Kustomize 应用这个 patch。在 Catalog Service staging overlay 的 `kustomization.yml` 中，将 `patch-env.yml` 列举出来：

**清单 14.12 让 Kustomize 应用环境变量的补丁**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - github.com/<your_github_username>/catalog-service/k8s?ref=main
patchesStrategicMerge:
  - patch-env.yml
```

`patchesStrategicMerge`：根据 strategic merge 策略应用到 base 清单上的补丁列表；`- patch-env.yml`：用于定制传递给 Catalog Service 容器的环境变量的补丁。

你可以用同样方法定制 Deployment 的许多方面，比如副本数量、存活探针、就绪探针、优雅停机超时、环境变量、卷等。

### 14.3.5 定制 ConfigMaps

Catalog Service base Kustomization 指示 Kustomize 从 `application.yml` 文件生成一个 `catalog-config` ConfigMap。要定制该 ConfigMap 中的值，主要有两种途径：整体替换 ConfigMap，或只覆盖应用中 staging 环境不同的值做覆盖。对第二种情形，可以依赖 Kustomize 的高级 patch 策略来覆盖某些值。

在处理 Spring Boot 时，我们可以利用 Spring profile 的能力。我们可以毫不修改现有 ConfigMap，而是添加 `application-staging.yml` 文件，并且我们知道，当 staging profile 启用时，该文件优先于 `application.yml`。最终产生的 ConfigMap 将包含的是两个文件的合并。

首先，在 Catalog Service 的 staging overlay 里创建 `application-staging.yml`。我们使用这个文件来为 `.greeting` 属性定义不同的值。由于我们像上次那样，把所用同一个 minikube 集群作为 staging 环境，那么支撑服务的 URL 和凭据会和开发环境相同。在本章之上，根据实际场景，通常需要做更多定制。

**清单 14.13 为 Catalog Service 的 staging 专属配置**

```yaml
polar:
  greeting: Welcome to the book catalog from a staging Kubernetes environment!
```

然后，我们可以选择 Kustomize 提供的 ConfigMap Generator，把在 staging 地产的 `application-staging.yml`（在 base 中定义的 `application.yml`）合并到同一个 `应用名称 catalog-config` ConfigMap 中。接下来请更新 staging overlay 的 `kustomization.yml` 文件：

**清单 14.14 在同一个 ConfigMap 中合并多个属性文件**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - github.com/<your_github_username>/catalog-service/k8s?ref=main
patchesStrategicMerge:
  - patch-env.yml
configMapGenerator:
  - behavior: merge
    files:
      - application-staging.yml
    name: catalog-config
```

`behavior: merge`：决定将此 ConfigMap 与 base KustomizationBUILD中定义的相同 ConfigMap 合并；`files`: 要额外添加进 ConfigMap 的属性文件；`name`: 与 base Kustomization 中所用的 ConfigMap 相同名称。

关于旧的 `application.yml` 我们不再需要了。简化之后，你会发现命令行的使用更便捷了。

### 14.3.6 定制镜像名称和版本

我们在 `catalog-service/k8s/deployment.yml` 中用 base Deployment 清单是本地的容器镜像，没有指定版本号（这表示使用 latest 标签）。在开发阶段是方便的，但对其他环境不适用。

如果你按操作，你已经有一份在 GitHub 仓库 catalog-service 中维护的 sources，以及之前在 Commit Stage 工作流中构建的、发布到 GitHub Container Registry 的镜像 `ghcr.io/<your_github_username>/catalog-service:latest`。下一章将涉及发布策略和版本。我们仍然会用 latest 标签。对于镜像名称，现在是时候开始从 registry 拉镜像，替换本地版本。

> 注：注意：发布给 GitHub Container Registry 的镜像与代码仓库有相同的可见性。我假设我们为系统构建的所有镜像都可以通过 GitHub Container Registry 公开获取。如果不是，去对应仓库页面并进入 Packages 部分。或从侧面板选择 Package Settings，滚动到底部，并通过 Click Change Visibility 公开包可用。

和之前处理环境变量类似，我们可以用 patch 修改 Deployment 资源的镜像，因为这是最常见且每次发版都要改的定制之一。Kustomize 提供更便捷的方式声明每个容器想使用的镜像名称和版本。更进一步，我们既可以直接编辑 `kustomization.yaml`，也可以使用 Kustomize CLI（作为 Kubernetes CLI 的一部分）来完成。让我们试试后者。

打开终端窗口，进入 Catalog Service 的 staging overlay（`kubernetes/applications/catalog-service/staging`），运行以下命令定义 catalog-service 容器镜像和版本。记得把 `<your_github_username>` 替换成你的 GitHub 用户名（小写）：

```bash
$ kustomize edit set image \
    catalog-svc=ghcr.io/<your_github_username>/catalog-service:latest
```

正如你在下列清单中看到的，这个命令会自动把新内容写入 `kustomization.yaml` 中。

**清单 14.15 配置容器镜像名称和版本**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - github.com/<your_github_username>/catalog-service/k8s?ref=main
patchesStrategicMerge:
  - patch-env.yml
configMapGenerator:
  - behavior: merge
    files:
      - application-staging.yml
    name: catalog-config
images:
  - name: catalog-service
    newName: ghcr.io/<your_github_username>/catalog-service
    newTag: latest
```

`name`：Deployment 清单中定义的容器名；`newName`：容器的新的镜像名（包含你小写的 GitHub 用户名）；`newTag`：容器的新标签（指向 `latest`）。

### 14.3.7 定制副本数

云原生应用应该具有高可用性，而 Catalog Service 目前不是。我们一直是单实例部署。如果它崩溃或由于高负载暂时不可用怎么办？我们就不能使用应用了。不够有弹性，不是吗？staging 环境尤其适合做负载和可用性测试。至少应该运行两个实例。Kustomize 提供了一种方便的方式来修改每个 Pod 的 replicas 数量。

打开 Catalog Service staging overlay 中的 `kustomization.yaml` 文件（`kubernetes/applications/catalog-service/staging` ），把应用的副本数量配置为 2。

**清单 14.16 配置 Catalog Service 容器的副本数**

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - github.com/<your_github_username>/catalog-service/k8s?ref=main
patchesStrategicMerge:
  - patch-env.yml
configMapGenerator:
  - behavior: merge
    files:
      - application-staging.yml
    name: catalog-config
images:
  - name: catalog-service
    newName: ghcr.io/<your_github_username>/catalog-service
    newTag: latest
replicas:
  - name: catalog-service
    count: 2
```

`replicas`：为 Deployment 定义副本数的部分；`name`：要定义的副本数的 Deployment 名称；`count`：副本数量。

终于到了部署 Catalog Service，并测试 staging overlay 提供的配置的时刻。为简单起见，我们使用同一个 minikube 本地集群作为 staging 环境。如果你之前还保留着 minikube 集群，直接用它就好。否则，可以用 `./create-cluster.sh` 启动它。脚本会启动一个 Kubernetes 集群，并部署 Polar Bookshop 需要的支撑服务。

打开终端窗口，进入 Catalog Service 的 staging overlay 目录（`applications/catalog-service/staging`），运行以下命令用 Kustomize 部署应用：

```bash
$ kubectl apply -k .
```

你可以通过 Kubernetes CLI（`kubectl get pod -l app=catalog-service`）或 Octant GUI（更多请参考第 7 章）监控执行结果。一旦应用可用且就绪，你可以用 CLI 查看应用日志：

```bash
$ kubectl logs deployment/catalog-service
```

第一条 Spring Boot 日志事件将告诉你 staging profile 已启用，这正是我们在 staging overlay 分区 patch 中设置的结果。

该应用并没有对集群外部暴露，但你可以使用端口转发功能将流量从本地 9001 端口转发到集群内运行于 80 端口的 Service 上：

```bash
$ kubectl port-forward service/catalog-service 9001:80
```

然后，另开新终端窗口，并在端口 9001 调用根端点：

```bash
$ http :9001
Welcome to the book catalog from a staging Kubernetes environment!
```

结果正是 `application-staging.yml` 里定义的 `polar.greeting` 值的定制消息。这正是我们所期望的。

> 注意：值得注意：如果向 `:9001/books` 发送 GET 请求，你会得到一个空列表。在 staging 中，我们尚未启用 testdata profile 去在启动后生成书籍；我们只希望在开发或测试环境中这么做。

我们在 staging overlay 中最后一项定制，就是累积要部署的副本数。用以下命令确认：

```bash
$ kubectl get pod -l app=catalog-service
NAME                        READY   STATUS    RESTARTS   AGE
catalog-service-5f6f8c7894f-7n2k2   1/1     Running   0          3m94s
catalog-service-5f6f8c7894f-w8bnq   1/1     Running   0          3m94s
```

Kubernetes 设计为大多数集群应用的可用性各不相同。如果某个节点有足够的剩余资源，它将会尝试在两个不同节点上运行两个副本。如果其中一个节点崩溃，应用在另一个节点上仍然可用。同时 Kubernetes 会新部署副本到 other node ，确保始终有两个副本。你可通过 `kubectl get pod -o wide` 查看每个 Pod 分配在哪个节点上。就我们的场景而言，minikube 集群只有一个节点，两个实例部署、它们会非常接近。

如果你好奇，你可以尝试更新 `application-staging.yml` 文件，再次运行 `kubectl apply -k .`，看看的 Pod 怎样逐个重启并把新 ConfigMap 装进来，从而验证滚动更新实现不掉服务。为了观察所发生的事件顺序，可以用 Octant，或在应用之前另开一个终端窗口运行 `kubectl get pods -l app=catalog-service --watch`。

应用测试完毕后，你可以用 Ctrl+C 终止端口转发进程，并删除之前创建的集群（`polldeploy/kubernetes/platform/development` 中的 `./destroy-cluster.sh`）。

### 小结

- 一个用 Spring Cloud Config Server 构建的配置服务器，可以用 Spring Security 提供的任何特性进行保护。예를 들어，你可以要求客户端使用 HTTP Basic 认证来访问服务器暴露的配置端点。
- Spring Boot 应用中的配置数据可以调用 Spring Boot Actuator 暴露的 `/actuator/refresh` 端点来重新加载。
- 要将配置刷新操作传播到其他应用程序，你可以使用 Spring Cloud Bus。
- Spring Cloud Config Server 的 Monitor 模块暴露了一个 `/monitor` 端点，代码仓库可以提供在一个新更改被推送到配置仓库之后，通过 webhook 调用它。结果是所有受影响的应用程序会通过 Spring Cloud Bus 触发配置刷新。整个过程完全自动。
- 管理密钥（secret）是任何软件系统中的关键任务，错误操作十分危险。
- Spring Cloud Config 支持加解密，以对称密钥或非对称密钥安全地处理配置仓库中的密钥。你也可以使用 Azure、AWS、Google Cloud 等云提供的密钥管理方案，借助 Spring Cloud Azure、Spring Cloud AWS、Spring Cloud GCP 集成到 Spring Boot。
- 你也可以把 HashiCorp Vault 作为 Spring Vault，供 Spring Boot 应用直接使用，或者作为 Spring Cloud Config Server 的 backend。
- 当 Spring Boot 应用部署到 Kubernetes 时，可以用 ConfigMaps 配置非敏感配置数据，用 Secrets 存储敏感配置信息。
- 可以以 Environment 变量或 mount 的方式使用 ConfigMaps 和 Secrets，Spring Boot 原生支持卷导入模式。后者是推荐做法。
- 在 Secrets 并不真正保密。其中包含的数据未加密，因此它不能纳入版本控制。
- 平台团队负责保护敏感信息，例如可以用 Sealed Secrets 项目进行加密并纳入版本控制。
- 管理多个 Kubernetes 清单来部署应用并不容易。Kustomize 提供了集中的方式来管理、部署、配置和升级 Kubernetes 上的应用。
- Kustomize 提供生成器来构造 ConfigMaps、Secrets，并在它们被更新时触发滚动重启。
- Kustomize 配置定制基于 base 和 overlays 的概念。overlay 构建在 base 之上，通过 patches 应用定制。你可以为环境变量、ConfigMaps、container image、replicas 定义 patch。
